# 3. Problem Statement & Expected Solution

## 3.1 Problem

A bank wants to cut customer onboarding turnaround time from seven days to under one hour. You build the full digital onboarding pipeline — lead capture, KYC document submission, AML / PEP screening, risk classification, manual review, and account auto-creation — under one constraint: **no manual coding.**

Every line of production code must be generated by Claude Code agents under your supervision.

## 3.2 Your Role

AI-Native Engineer — architect, supervisor, and quality gatekeeper. You write specifications, configure agents, install guardrails, and review pull requests. You do not write production code by hand.

## 3.3 Expected Solution

A working platform delivered as a Git repository that demonstrates:

* A complete AI-native engineering substrate built on the Claude Harness Engine plugin foundation, extended with customer-onboarding-specific specs, agents, skills, hooks, commands, and MCP integration.
* A functional onboarding platform built end-to-end by Claude Code agents — covering lead capture, KYC document workflow, rule-based AML / PEP screening, risk-band classification, compliance officer review, and account creation — with no hand-written production code.
* An evidence trail (PRs, agent logs, post-mortems, sprint contracts) proving the work was agent-led.

## 3.4 Applicable Rules

* **No-Hand-Coding Rule.** All production code, tests, and migrations must be generated by Claude Code agents. Hand-edits are limited to specs, CLAUDE.md, agent definitions, hooks, skills, and other substrate files.
* **Spec-Is-Truth Rule.** Whenever a spec and code disagree, the spec wins. Update the spec deliberately and regenerate the code.
* **PR-Only Merge Rule.** No direct commits to main. All changes flow through agent-reviewed pull requests.
* **Synthetic-Data Rule.** Use only dummy data. Do not use Virtusa confidential or customer-sensitive data for this project.

# 5. Acceptance Criteria & Non-Functional Requirements

## 5.1 Functional Acceptance Criteria

### AC-01

Prospect can register a lead with name, contact, and intended product (Savings / Current / NRE); the lead enters **INITIATED** state and is assigned a `case_id`.

### AC-02

Prospect can upload KYC documents per a product-specific checklist (ID proof, address proof, photograph, plus product-specific items); missing documents prevent submission.

### AC-03

A stubbed document-classification step returns canned results for known fixture files (PAN, Aadhaar, passport, utility-bill, etc.) and flags unrecognised uploads.

### AC-04

Onboarding lifecycle: **INITIATED → DOCS_SUBMITTED → SCREENED → CLASSIFIED → APPROVED / REJECTED / MANUAL_REVIEW**, with invalid transitions raising `InvalidOnboardingStateException`.

### AC-05

AML / PEP screening evaluates the prospect's name against a small static watchlist; any hit moves the case to **MANUAL_REVIEW** with reason code.

### AC-06

Risk-band classification uses a versioned rule engine (age, declared income band, occupation category, geography) to assign **LOW / MEDIUM / HIGH**; published rule versions are immutable.

### AC-07

Auto-approval logic: a LOW-risk case with no AML hit and all documents verified moves to **APPROVED** state and triggers stubbed account creation.

### AC-08

Compliance officer can review MANUAL_REVIEW cases and override the decision (APPROVE / REJECT) with a reason code; the override action is audited.

### AC-09

Prospect receives a stubbed notification at each state transition and can re-upload missing or rejected documents without restarting the case.

### AC-10

Admin can view onboarding turnaround time by product, approval funnel, manual-review backlog, average time-per-stage, and top rejection reasons.

**Note.** Each AC must have at least one test referencing its AC-NN identifier.

---

## 5.2 Non-Functional Requirements

### NFR-01

Risk-band thresholds and scoring weights are stored and computed as fixed-point or integer values — never floating-point.

### NFR-02

KYC document records, screening results, decisions, and override actions are all append-only.

### NFR-03

PII (PAN, Aadhaar, contact details, declared income, occupation) is never written to logs in plaintext.

### NFR-04

Authentication boundary at controller layer; prospect / KYC-analyst / compliance-officer / admin roles are separated.

### NFR-05

Database migrations, classification-rule migrations, and watchlist migrations are append-only.

### NFR-06

Structured JSON logs with request correlation IDs and `case_id`.

### NFR-07

Health endpoint returns 200 within 1 second of a successful startup.

### NFR-08

Architecture rules enforced as tests — published classification rules cannot be mutated; an approved case cannot be modified; risk-band re-assignment requires an override audit record.

# 6. Functional Scope

## 6.1 Customer / End-User Functionality (User Journeys)

* **Register Lead.** Provide name, contact, and intended product; receive a case ID and applicable document checklist.
* **Upload Documents.** Upload required documents per the product checklist; receive immediate classification feedback.
* **Track Status.** View case timeline (state transitions, queries, decisions) and reason codes.
* **Re-Upload.** Re-upload missing or rejected documents without restarting the case.
* **Account Activation.** Receive account-opening confirmation on approval (stubbed account creation).

## 6.2 Internal & System Functionality

* **KYC Analyst Workbench.** Review submitted documents, mark each as VERIFIED / REJECTED with reason, manage queries.
* **Compliance Officer Queue.** Handle MANUAL_REVIEW cases (AML hits, ambiguous classifications), override decisions with audit trail.
* **AML / PEP Screening Engine.** Rule-based watchlist evaluation; hit reasons captured with rule reference and timestamp.
* **Risk Classification Engine.** Versioned rule engine producing LOW / MEDIUM / HIGH risk band per prospect.
* **Admin Console.** Manage product document checklists, classification-rule library, watchlist, and user / role configuration.
* **Reports.** TAT by product, funnel conversion, manual-review backlog, top rejection reasons, dropped-lead analysis.

## 6.3 Out of Scope

You do not need to build:

* Real OCR / document-extraction engine — classification is stubbed
* Real CKYC or e-KYC registry integration
* Real video KYC / liveness detection
* Real digital signature / Aadhaar e-sign integration
* Real account creation in core banking — final step is stubbed
* Production deployment, secret management, multi-region

**Foundation.** Install the Claude Harness Engine plugin first. The harness ships 7 base agents (planner, generator, evaluator, security-reviewer, test-engineer, design-critic, ui-designer), 12+ hooks, base commands, sprint contracts, an evaluator wired to Playwright MCP, and a self-healing loop.

On top of that foundation, your repository must add the project-specific substrate listed in this section.

The rubric scores the final repository — both Harness-supplied and learner-added artifacts contribute, but the thresholds below are calibrated so that learners who only install Harness without customizing for the project domain will not meet them.
