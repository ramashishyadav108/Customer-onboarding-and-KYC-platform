## 2. Shared files (touched by several stories)

Because these files are modified across groups, the `/build` team lead must serialise edits per group (two stories in the same group never modify the same shared file; exceptions are noted).

| File | Stories in order |
|---|---|
| `BE main.py` | E1-S1, E1-S2, E1-S3 (routers), then each API story adds one `include_router` line; E5-S3 last |
| `BE controllers/error_handlers.py` | E1-S2 (create, 401/403), E1-S4 (INVALID_STATE), E4-S1 (CASE_LOCKED), E3-S4 (RULESET_*) |
| `BE controllers/routers/pipeline.py` | E3-S1 (screen), E3-S3 (classify), E4-S1 (decide, advance) |
| `BE controllers/routers/documents.py` | E2-S1, E2-S2 (submit), E2-S4 (reject) |
| `BE services/case_view_service.py` | E1-S3, E2-S2, E2-S4, E3-S5 |
| `BE repositories/models/*.py` | Model classes are created in the stories above; `0001_core_schema.py` (E1-S1) creates every table once so later stories add no schema migration except seeds. A missing column discovered later is a NEW migration, never an edit |
| `frontend/src/main.tsx` | E1-S1, E2-S5, E4-S5, E5-S4 (routes) |

**Dependency amendment proposed:** E1-S4, E1-S5 and E3-S2 are in Group A with no declared dependency, but their integration tests need the schema, settings and database session from E1-S1. `/build` must run E1-S1 first within Group A (or add `E1-S1` to their `depends_on`; this changes the graph's group letters only for ordering inside A, not for any later group).

Note on E1-S1 creating all tables and triggers: the stories have different owners but the schema is a single design (`data-models.md`). Creating it in one migration avoids cross-group migration ordering conflicts and keeps the migration guard simple. Seed migrations (`0003` to `0007`) belong to the stories that own the data.
