# E1-S3: Prospect can register a lead and receive a case ID

- **Epic:** E1 - Lead Capture, Foundation and Checklist (Sprint 1)
- **Layer:** API
- **Group:** C
- **depends_on:** E1-S2, E1-S4, E1-S5
- **Covers:** AC-01, NFR-03

## Description

A prospect starts onboarding by submitting name, contact and product. The system creates a case in INITIATED and returns a case_id. The prospect then supplies the profile fields the risk rules need.

## Acceptance Criteria

1. POST /api/v1/leads with name, contact (10-digit phone or valid email) and product in {Savings, Current, NRE} returns 201 with a UUID case_id and state INITIATED.
2. Missing name, missing contact, malformed contact, or a product outside the enum returns 422 with a field-level error list and creates no case.
3. Creating a lead appends an audit entry (event LEAD_CREATED, actor, case_id, UTC timestamp) and an initial state-history row for INITIATED in the same transaction.
4. GET /api/v1/cases/{case_id} returns state, product, checklist version and the checklist items for the product; contact is returned masked (only last 2 characters visible).
5. PUT /api/v1/cases/{case_id}/profile stores date_of_birth, annual_income (integer INR), occupation_category (enum) and country_code while the case is INITIATED; it returns 409 once the state is DOCS_SUBMITTED or later, and rejects non-integer income with 422.
6. Sending the same Idempotency-Key header on two identical POST /api/v1/leads calls returns the same case_id (second response 200) and leaves exactly one case row.
