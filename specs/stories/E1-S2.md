# E1-S2: User can authenticate with a token and is restricted by role

- **Epic:** E1 - Lead Capture, Foundation and Checklist (Sprint 1)
- **Layer:** API
- **Group:** B
- **depends_on:** E1-S1
- **Covers:** NFR-04, NFR-03

## Description

Four roles (prospect, kyc-analyst, compliance-officer, admin) must be separated. Authentication is token-based with seeded synthetic users, and authorization is enforced at the controller layer only.

## Acceptance Criteria

1. POST /api/v1/auth/login with a seeded synthetic username and password returns 200 with access_token, token_type bearer and role; wrong password returns 401 with no indication of which field was wrong.
2. A migration seeds exactly one synthetic user for each of the roles prospect, kyc-analyst, compliance-officer and admin; passwords are stored as salted hashes and never appear in responses or logs.
3. A protected endpoint called without a token returns 401, and with a valid token of an unauthorised role returns 403; role checks live in controller dependencies and no module under service/ or repository/ imports the auth dependency module.
4. Access tokens expire after a configurable TTL (default 1800 seconds); a token presented after expiry returns 401.
5. A prospect token is bound to one case_id; requesting GET /api/v1/cases/{other_case_id} with it returns 403, while staff roles can read any case.
