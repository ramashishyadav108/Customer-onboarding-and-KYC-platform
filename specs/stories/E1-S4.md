# E1-S4: Onboarding state machine enforces the lifecycle and audits every transition

- **Epic:** E1 - Lead Capture, Foundation and Checklist (Sprint 1)
- **Layer:** Service
- **Group:** A
- **depends_on:** []
- **Covers:** AC-04, NFR-02

## Description

Architecture option B: a persisted state machine with a transition table. Every state change goes through one service function, is audited, and invalid transitions raise InvalidOnboardingStateException.

## Acceptance Criteria

1. The transition table permits exactly these edges and no others: INITIATED->DOCS_SUBMITTED, DOCS_SUBMITTED->SCREENED, SCREENED->CLASSIFIED, CLASSIFIED->APPROVED, CLASSIFIED->REJECTED, CLASSIFIED->MANUAL_REVIEW, MANUAL_REVIEW->APPROVED, MANUAL_REVIEW->REJECTED.
2. An invalid transition raises InvalidOnboardingStateException carrying case_id, from_state and to_state, leaves the state unchanged, and the API maps it to HTTP 409 with error code INVALID_STATE.
3. Each successful transition appends a state-history row (case_id, from_state, to_state, actor, reason_code, UTC timestamp) in the same DB transaction as the state update; a forced failure after the update rolls both back.
4. APPROVED and REJECTED are terminal: every transition attempted out of either state raises InvalidOnboardingStateException.
5. State-history and audit-log tables are append-only: an UPDATE or DELETE against either is rejected by the database (trigger) and the repository layer exposes no update or delete method for them.
6. Repeating a transition request with the same idempotency key returns the original result and does not add a second history row.
